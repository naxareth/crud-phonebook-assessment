# Phonebook Assessment Plan

## *Full stack development intern assessment*

Build a working phonebook in two hours using React with Vite, an Express API, and Supabase PostgreSQL. This plan defines the agreed scope, implementation sequence, deployment needs, and demonstration checklist. It describes planned work, not a completed application.

# **Assessment requirements**

The supplied assessment screenshot requests a phonebook with Create, Read, Update, and Delete operations. Any language and database may be used, and AI assistance is allowed. Presentation begins after two hours whether the application is finished or unfinished.

Deployment is an additional project goal discussed during planning; it is not stated as a requirement in the screenshot. Contact fields, validation rules, and interface details below are implementation decisions.

# **Must have functionality**

| Feature | Acceptance criteria |
| :---- | :---- |
| Create | Save a contact with a name and phone number; email is optional. |
| Read | Display contacts from the database and show an empty state when none exist. |
| Update | Edit a selected contact and display the saved values. |
| Delete | Ask for confirmation, then remove the selected contact. |
| Persistence | Saved contacts remain after page refresh and application redeployment. |
| Validation | Reject blank names and phone numbers; check email format when provided. |
| Interface feedback | Show loading, success, and error states; prevent duplicate submissions. |

# **Scope boundaries**

Search and additional styling are optional after CRUD works. Authentication, contact imports, photo uploads, and advanced features are outside the agreed minimum. Use fictional contacts for the assessment demo. A public app storing personal contacts would need appropriate access controls.

# **Technology and architecture**

| Layer | Selected technology | Responsibility |
| :---- | :---- | :---- |
| Frontend | React and Vite | Contact list, forms, validation feedback, and API requests. |
| Backend | Node.js and Express | CRUD routes, server-side validation, and consistent errors. |
| Database | Supabase PostgreSQL | Persistent contact records and database constraints. |
| Language | JavaScript | Shared language across frontend and backend. |
| Styling | Plain CSS | Responsive and readable interface without extra UI setup. |

Request flow: React frontend → Express API → Supabase PostgreSQL. In production, Express serves the built frontend and the /api routes from one origin. React calls relative URLs such as /api/contacts.

# **Why Supabase**

Supabase keeps the database separate from application hosting, avoiding the persistent local disk requirement of SQLite. Its PostgreSQL database supports a structured contact schema. Its generated Data API can simplify database access, while our Express layer makes custom backend validation and request handling visible in the assessment. \[1\]

Keeping Express introduces more code and deployment work than React calling Supabase directly. We accept that tradeoff to demonstrate backend development. Supabase also introduces an external service and network dependency; connection failures must be handled clearly.

# **Interview explanation**

“I chose React, Express, and Supabase PostgreSQL to deliver a persistent CRUD phonebook within the time limit. React handles the interface, Express validates requests and exposes the API, and Supabase hosts the database. This separation lets me demonstrate frontend and backend skills while reducing database infrastructure setup.”

# **Server access and credentials**

Proposed implementation: Express uses the Supabase JavaScript client to access the contacts table through the Data API. Store SUPABASE\_URL and a server-only Supabase secret key in environment variables. Never put a secret or service-role key in React code or a VITE\_ variable. These privileged keys can bypass Row Level Security, so Express remains responsible for validating requests and enforcing any application authorization. \[2\]

Enable Row Level Security on the contacts table and do not grant anonymous browser CRUD access for this server-only design. RLS does not secure an unprotected Express route when the server uses a privileged key. Keep the assessment dataset fictional; add authentication and authorization before storing private contacts publicly. \[2, 3\]

# **Database and API design**

Use one contacts table. The schema below is a proposed implementation detail rather than an additional assessment requirement.

| Field | Type | Rule |
| :---- | :---- | :---- |
| id | uuid | Primary key generated by the database. |
| name | text | Required; trim whitespace and reject empty values. |
| phone | text | Required; preserve leading zeros and the \+ prefix. |
| email | text | Optional; store omitted values as NULL. |
| created\_at | timestamptz | Default to the database insertion time. |

Validate on the server even when the form validates too. Keep phone validation permissive enough for international formats; do not convert phone numbers to numeric values. Use database NOT NULL and nonblank constraints for required fields. Duplicate-contact blocking is not part of the minimum scope.

| Method | Endpoint | Result |
| :---- | :---- | :---- |
| GET | /api/contacts | 200 with the contact list; \[\] when empty. |
| POST | /api/contacts | 201 with the created contact. |
| PUT | /api/contacts/:id | 200 with the updated contact. |
| DELETE | /api/contacts/:id | 204 after deleting the contact. |

POST and PUT accept name, phone, and optional email. Return 400 for invalid fields or malformed IDs, 404 when a target contact does not exist, and a generic 500 response for unexpected server errors. Use a consistent error body such as {"error":"Name is required"}. Keep database internals out of user-facing responses.

# **Frontend behavior**

Use a single main screen with a contact list and a reusable add/edit form. Selecting Edit fills the form with that contact. Cancel returns to the normal state. After a successful mutation, refresh the list from the API. Show clear form labels, disable Save while pending, and preserve entered values if saving fails.

# **Suggested project organization**

client/ contains React components and CSS. server/ contains Express routes, validation, and the Supabase client. supabase/schema.sql contains the repeatable table setup. Include .env.example, .gitignore, and a README with local setup, database setup, production commands, and known limitations.

# **Two hour execution plan**

This schedule budgets the full assessment window. If some time has already elapsed, reduce styling and optional work while protecting CRUD verification and presentation time.

| Minutes | Task | Checkpoint |
| :---- | :---- | :---- |
| 0–10 | Set up app and Supabase table | Frontend and server start; database is reachable. |
| 10–35 | Implement API and validation | All four CRUD operations work through the API. |
| 35–70 | Build and connect the interface | Complete create, view, edit, and delete flow. |
| 70–90 | Validate and test locally | Errors, empty state, and persistence verified. |
| 90–115 | Deploy and test hosted app | Public URL loads; CRUD and persistence work. |
| 115–120 | Prepare presentation | Demo sequence and limitations are ready. |

# **Deployment checklist**

* Choose an application host that runs Node.js. The hosting provider and account remain undecided; Supabase hosts the database, not the Express application in this plan.  
* Define a production build for React and a start command for Express. Read PORT from the environment and serve the built frontend with API routes registered first.  
* Configure server-only Supabase environment variables on the host. Commit .env.example with placeholders; exclude real credentials from Git.  
* Apply the contacts schema, verify RLS settings, then test create, read, update, and delete through the deployed application.  
* Refresh and redeploy the application to verify that Supabase records persist. If deployment is blocked, present the working local application and explain the remaining setup.

# **Verification and presentation**

Test a valid contact, a leading-zero or international phone number, an omitted email, blank required fields, an invalid email, editing, canceling deletion, confirming deletion, and a database/API failure. Confirm the interface recovers without falsely reporting success.

Demo sequence: explain the architecture, create a fictional contact, edit it, refresh to show persistence, demonstrate validation, then delete the contact. Close with the Supabase rationale and honest limitations. Present at the deadline even if unfinished.
